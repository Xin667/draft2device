# How Draft2Device Works, and Why We Built It This Way

Draft2Device turns an analog storyboard sketch into working hardware specs and source code. A person uploads a drawing of an idea, perhaps with a few handwritten notes, and walks through a six-step wizard that ends with a circuit diagram, generated firmware, and a PDF they can print and take to a workbench. This document explains how the pieces fit together technically and why each major technology was chosen over the alternatives.

## The shape of the system

The repository is a monorepo: frontend, backend, and database live in one place so the whole project can be cloned and run end to end without juggling multiple repositories or version-mismatched services. The frontend is a Vite-built React application that talks to a FastAPI backend over plain HTTP, proxied during development so the browser never has to deal with CORS. The backend holds all of the OpenAI calls, all of the persistence, and nothing else lives outside of it, which means the frontend can be rebuilt, redesigned, or even replaced without touching how a project is analyzed, priced out in hardware, wired into a circuit, or turned into code.

Every unit of work in the backend is organized the same way: one folder per endpoint under `backend/endpoints/`, each with its own `router.py`, `schema.py`, and `prompt.py`. Nothing endpoint-specific leaks into `backend/config.py`, which holds only what every endpoint shares: the OpenAI client, the model name, and the switch that controls how aggressively old images get resent to the model. That separation is deliberate. Five people could work on five endpoints in parallel without stepping on each other's prompts or schemas, and in fact the backend's own comments note that the `analyze` and `hardware` routers were merged in from two previously separate FastAPI apps, which only worked cleanly because the endpoint-per-folder convention was already in place.

## The pipeline behind the six steps

The wizard's six steps map onto five backend endpoints plus one small helper:

| Step | What the user does | Endpoint |
| --- | --- | --- |
| 1. Input | Upload a sketch, add notes | `POST /analyze` |
| 2. Clarification | Answer the model's open questions | `POST /analyze` (again, with answers) |
| 3. Hardware | Review and swap suggested components | `POST /hardware`, `POST /hardware/select` |
| 4. Circuit diagram | Review the wiring, request changes | `POST /circuit-diagram` |
| 5. Source code | Fill in config values (Wi-Fi SSID, pins, …) | `POST /code`, `POST /code/{id}/answers` |
| 6. Result | Export as PDF or JSON | reads the artifacts already stored |

A small glossary endpoint (`POST /api/glossary/extract-and-explain`) runs alongside this pipeline rather than inside it: it has no project ID and writes nothing to the database, it just takes a snippet of text and returns plain-language explanations of the hardware terms in it, which the frontend renders as hover tooltips. It also has no fallback requirement of its own, since the frontend keeps a static glossary (`lib/glossary-match.ts`) to fall back on if the AI call fails.

Each real pipeline step follows the same pattern underneath. A project is created once (`POST /projects`), which gives it a UUID. From there, every endpoint reads whatever the previous step produced, calls the model, and writes its result back as a new row rather than overwriting the old one, so the full history of a project's analysis, hardware choices, and circuit revisions stays intact. Two SQLite tables make this possible: `messages`, which holds the full chat history per endpoint (tagged by a `conversation_type` so the `/analyze` conversation and the `/hardware` conversation about the same project never mix), and `artifacts`, which holds the structured JSON result of each step, also versioned by insertion rather than updated in place. A fourth table, `images`, stores uploaded sketches as binary blobs tied to the specific chat message they arrived with.

That history is what makes refinement possible. Asking the model to reconsider a decision at step 3 or 4 does not start over; it replays the endpoint's own stored conversation and appends the new request, so the model still remembers earlier context. The circuit diagram endpoint goes one step further: if a change request there actually implies a different physical component (swapping an LED for a buzzer, say), it first classifies whether the request even touches the hardware list, and only if it does, triggers a targeted refinement call back into the `/hardware` conversation before regenerating the diagram. Wiring that logic into a single endpoint, rather than forcing the user to manually go back a step, is only possible because each stage's chat history and artifacts are kept separately addressable in the database.

## Why these technologies

### React, TypeScript, and Vite for the frontend

The wizard is six interactive screens sharing one piece of in-progress project state, so the natural fit is a component framework rather than hand-rolled DOM manipulation. React gives each step its own component (`features/step1-input`, `features/step2-klaerung`, and so on) while the shell (`app/AppShell.tsx`, `app/Navigation.tsx`) stays responsible for the stepper and layout around them. TypeScript catches a class of bugs that would otherwise only surface at runtime, which matters here specifically because the data shapes coming back from the AI are large and nested: a hardware component has options, each option has a dozen optional fields, a circuit diagram has components, pins, and connections that all reference each other by ID. The normalization layer in `api/api.ts` leans on those types to coerce whatever JSON the backend returns into something the rest of the app can trust. Vite rounds this out with a fast dev server and a quick build, and its built-in proxy (`vite.config.ts`) is what lets the frontend talk to `/analyze`, `/hardware`, `/circuit-diagram`, and `/code` on `localhost:5173` during development without a CORS workaround.

### Tailwind CSS and shadcn/ui for the design

Styling six wizard steps consistently, plus a navigation shell, a project history panel, and an interactive schematic viewer, is a lot of surface area to keep visually coherent by hand. Tailwind's utility classes let every component carry its own styling inline without drifting into a dozen slightly different button styles across files. shadcn/ui supplies the pieces that are tedious to get right from scratch, like the button, hover card, and tooltip primitives under `components/ui/`, already wired to the project's own color palette (`components.json` pins a neutral base color and the "base-nova" style) instead of a generic default theme. The combination means new UI can be assembled from existing, already-consistent parts rather than redesigned per screen.

### Zustand for state, and TanStack Query for server data

These two solve different problems, which is exactly why the project uses both instead of picking one and stretching it. Zustand owns state that belongs to the UI and to the pipeline itself: which step is active, how far the user has progressed, the sketch file sitting in step 1 before it is ever sent anywhere, and the project's accumulated results (`structure`, `hardwareData`, `circuitData`) once they come back from the backend. That lives in `store/state.ts` and the smaller `app/store.ts`, and it is intentionally just a plain store with setters and a handful of async actions like `submitAnalyze` or `chooseHardware` that call the API layer and then update state with the result.

TanStack Query is set up at the root of the app (`main.tsx` wraps everything in a `QueryClientProvider`) to be the layer responsible for request caching, retries, and loading and error states around server responses, as distinct from state the UI invents on its own. Keeping that boundary explicit avoids a common failure mode in apps that try to do everything in one global store: UI state and server state end up with different lifetimes and different correctness rules (server data can go stale, UI state generally can't), and conflating them tends to produce bugs where a stale cache and a user's in-progress edit fight over the same field.

### React Hook Form and Zod for forms and validation

Both are part of the dependency set specifically so the more input-heavy steps, the configuration answers in step 5 being the clearest example, have a defined way to validate input locally before it goes anywhere near the model or the backend. A Zod schema describing what a valid answer looks like, paired with React Hook Form managing the field state, means a malformed or missing value can be caught and explained to the user immediately instead of being discovered only after a wasted API call. At the moment the simplest screens, like the sketch-and-notes upload in step 1, get by on plain React state, since there is little to validate there beyond "is anything there at all." The two libraries are the intended mechanism for the steps where validation actually earns its keep.

### FastAPI for the backend

FastAPI was chosen for two practical reasons beyond general preference for Python in an AI-heavy backend. First, Pydantic models double as both request validation and, for endpoints like `/circuit-diagram` and `/code`, as the literal schema handed to OpenAI's structured output feature: `client.chat.completions.parse(response_format=CircuitDiagram)` builds its JSON schema straight from the same `CircuitDiagram` class that validates the HTTP response, so the schema is defined exactly once. Second, FastAPI generates interactive API documentation for free at `/docs`, which during a project built by several people working on separate endpoints in parallel meant nobody had to hand-write or maintain a shared API reference; the running server always has the up-to-date one. The pipeline's structure, each endpoint reading one artifact type and writing another, also made it straightforward to write a single pytest file (`tests/test_pipeline_flow.py`) that walks `/projects` through `/analyze`, `/hardware`, and `/circuit-diagram` with every model call mocked, so the integration is checked without spending any API budget.

### The OpenAI API for multimodal reasoning

A central, single-source client in `config.py` is used for every AI call in the backend, so the model name and API key are defined exactly once rather than duplicated per endpoint. What changes between endpoints is which OpenAI API surface gets used, and that choice is made deliberately rather than out of habit. `/analyze` needs to reason over an uploaded sketch together with typed notes, so it builds Chat Completions messages where an image is attached as a base64 data URL alongside the text, letting the model read a drawing and a description as one combined input. `/hardware` needs live web search for current prices and availability, and the web search tool is only available through the Responses API, so that endpoint calls `client.responses.create` instead, with a German-market location hint attached when local sourcing is requested. `/circuit-diagram` and `/code` need neither images nor browsing, only a strict, nested JSON structure back, so they use `client.chat.completions.parse` against a Pydantic schema and get a validated object back directly instead of a raw string to parse by hand.

Cost is managed at the same central point: a single switch in `config.py` (`RESEND_ALL_IMAGES_EVERY_REQUEST`) decides whether older uploaded images get resent to the model on every follow-up message or only once, at the moment they were uploaded. Turned off, as it is by default, a later question like "look at the sketch again" will not reliably work, but token costs stay flat instead of growing with every additional refinement round. Which image formats, model capabilities, and output shapes are actually available in practice still depends on the specific model configured in `config.py` and the prompt written for each endpoint; the architecture here is about keeping that choice swappable in one place, not about guaranteeing any particular capability forever.

### SQLite for storage

A prototype that a reviewer should be able to clone and run immediately does not benefit from a separate database server to install, configure, and keep running. SQLite is a single file (`backend/db/draft2device.db`), its schema is created automatically on server start if the file doesn't already have it, and that file is deliberately committed to the repository so that demo projects, complete with their analysis, hardware choices, circuit diagrams, and generated code, are already there the moment someone clones the repo. The four-table design (`projects`, `messages`, `artifacts`, `images`) keeps each project's chat history, structured results, and uploaded images separately queryable, while still being simple enough to reason about without an ORM in between.

This choice does carry a real limit: SQLite serializes writes, so it is not the right fit for many concurrent writers or multiple backend instances behind a load balancer. If the project moved from demo to something serving many simultaneous users, PostgreSQL would be the natural next step, since the access pattern here (a handful of tables, simple key lookups by project ID) would carry over with very little change beyond the connection layer itself.
